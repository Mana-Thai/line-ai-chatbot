# 家計簿アプリ(SCB Connect通知連携)制作プラン

グループLINEで使っている注文とりまとめアプリの実証済み構成を雛形に、
**SCB(サイアム商業銀行)のLINE通知をもとに家計簿を自動更新するWebアプリ**を作るためのプラン。

## 0. 前提(ヒアリング済み・確定事項)

| 項目 | 確定内容 |
|---|---|
| 銀行 | **SCB Connect**(LINE公式アカウントからの入出金通知) |
| 使う人 | **本人1人のみ** → 認証は合言葉(パスコード)方式で最速化。権限分けは不要 |
| 通知の言語 | タイ語(項目名固定)。金額・日付・相手名は数字/タイ語/英語混在 |
| これまでの管理 | Googleスプレッドシート。日付×カテゴリ列のマトリクス+**日次残高照合(Adjust列で差額0確認)** |
| 自分の口座 | X-4211(通知内の「จากบัญชี/เข้าบัญชี」のうち自分側。設定画面で登録制にする) |

### 通知フォーマット(実サンプル3枚から確認済み)

SCB Connectの通知はカード型で項目が完全に固定:

| 項目 | 入金例 | 出金(振込)例 |
|---|---|---|
| 種別 | รายการเงินเข้า(入金) | รายการเงินออก(出金) |
| 金額 | +1,600.00 บาท | -115.00 บาท |
| จากบัญชี(送金元) | นาง จันทรัตน์ X-8110 ออมสิน | X-4211(自分) |
| เข้าบัญชี(送金先) | X-4211(自分) | SANGNAPA MANE X-4314 ไทยพาณิชย์ |
| วันที่/เวลา(日時) | 28/07/2026 21:05 | 30/07/2026 17:18 |
| ยอดเงินที่ใช้ได้(利用可能残高) | 3,809.41 บาท | 650.97 บาท |

→ **相手口座(名前+マスク口座番号+銀行名)が必ず入っている**ので自動入力できる。
→ **残高が毎回入っている**ので、Excelでやっていた残高照合(Adjust)も自動化できる。

## 1. 要件と実現方法

| 要件 | 実現方法 |
|---|---|
| 銀行LINE通知を元に家計簿を更新 | 通知の**スクリーンショットを取り込み**、AI画像解析で自動記帳(§2) |
| 現金の買い物は手動入力 | 金額→カテゴリ大ボタン→登録の2タップクイック入力 |
| 立ち上げ最速・簡単に使える | 雛形流用+合言葉ログイン+スマホ3画面のみ |
| 相手口座内容の自動入力 | 通知からจากบัญชี/เข้าบัญชีを抽出し、自分の口座(X-4211)でない側を相手として記録。**学習辞書**でカテゴリも自動補完(§5) |

## 2. 最重要の設計判断:通知の取り込み方式

SCB Connectの通知は**Flexメッセージ(リッチカード)のため、長押しコピーでテキスト化できない**。
また通知に外部から読み取れる公開APIも無い。そこで**スクリーンショット取り込み**を軸に、段階的に2方式でいく。

### 方式A:スクショアップロード(Phase 1・MVP)

1. 通知が来たらスクショ(既に日常操作)
2. 家計簿アプリの「スクショ取り込み」ボタン→画像選択(複数枚まとめて可)
3. サーバーがAI画像解析(§5)で 種別・金額・相手・日時・残高 を抽出しプレビュー表示
4. カテゴリは学習辞書が自動提案 → 「登録」を押すだけ

- 実装は「画像アップロードAPI+解析1関数+プレビュー画面」だけで最速
- 解析に失敗した画像は手動フォームにフォールバック(金額だけ手直しして登録)

### 方式B:LINE転送Bot(Phase 2・自動化)

1. Messaging APIのBotを1対1トークに追加
2. 通知のスクショを**Botに転送(画像として共有)するだけ**
3. Webhookが画像を取得→同じ解析関数で自動記帳し、結果を返信
   (例:「✅ 出金 115.00 THB / 相手: SANGNAPA MANE (SCB) / カテゴリ: Food / 残高照合 OK」)

- 画像メッセージはBotで確実に受信できる(Flexカード本体は転送不可のためスクショ経由が正解)
- 旧チャットボット(`index.js`)のMessaging API実装と `@line/bot-sdk` を流用。解析関数は方式Aと完全共通

> 銀行スクレイピング等の完全自動読み取りは規約・安全性の面でやらない。
> 「スクショをBotに送るだけ」が運用負荷の現実的な下限。

## 3. 全体構成(雛形からの流用)

新しいリポジトリ(例: `kakeibo-app`)を作り、注文アプリからコピーする。

| ファイル | 流用方法 |
|---|---|
| `lib/auth.js` | HMACセッション+devログインを流用。**LINEログインは使わず合言葉(`APP_PASSCODE`)のみ**に簡略化(1人利用のため。LIFFチャネル設定が不要になり立ち上げが速い) |
| `lib/store.js` | 二重保存層(PostgreSQL/ローカルJSON)+起動時マイグレーション+`settings` の構造を残し、`orders` を `transactions` に書き換え |
| `server.js` | `requireAuth`・`/api/config`・`/healthz`・SSE を流用。注文APIを取引API+画像取り込みAPIに置き換え |
| `public/` | `api()` fetchラッパ・`escapeHtml`・`openStream`・画面切り替え構造を流用 |
| `shared/constants.js` | カテゴリ一覧(§4)のUMD共用パターン |
| `render.yaml` / `.env.example` | コピーしてサービス名・環境変数(`APP_PASSCODE`・`GEMINI_API_KEY` 等)を書き換え |

## 4. データモデルとカテゴリ

### transactions(1エンティティから開始)

```
transaction {
  id,
  date,                 // 取引日時(通知のวันที่/เวลา or 手動入力日)
  type,                 // income | expense
  amount,               // 金額(THB、小数2桁)
  source,               // screenshot | bot | cash(手動)
  counterparty,         // 相手名(例: "SANGNAPA MANE")
  counterparty_account, // 相手口座(例: "X-4314")
  counterparty_bank,    // 相手銀行(例: "ไทยพาณิชย์(SCB)" / "ออมสิน(GSB)")
  category,             // §4のカテゴリ
  balance_after,        // 通知の利用可能残高(残高照合に使用)
  memo,
  image_ref,            // 取り込み元スクショ(再確認・監査用に保持)
  created_at, updated_at
}
```

- **重複防止**: 「同日時・同額・同相手」一致で取り込み時に警告(同じスクショの二重取り込み対策)
- **残高照合**: 最新取引の `balance_after` と登録済み取引から計算した残高を突合し、
  差額があればExcelのAdjust列と同様に「調整」取引の作成を提案

### カテゴリ初期セット(現行スプレッドシートの列をそのまま採用)

- **収入(In)**: Salary / Allowance / RYUSEI / Investment
- **支出(Out)**: Food / Alcohol / Car (C) / Car (P) / Mobile / Apartment / Consumables /
  Health / Exercise / Study / Utilities / Clothes / Entertainment / Family / Pet /
  Investment / Cooperation / Debt
- **その他**: Adjust(残高調整用)

カテゴリは `settings` で追加・並べ替え可能にする(スプレッドシートと同じ英語名で運用継続)。

## 5. 通知スクショの解析と相手口座の自動入力

### 解析エンジン

- スクショ画像を **AI画像解析(構造化出力)** にかけ、固定項目をJSONで抽出する:
  `{ direction, amount, from_name, from_account, from_bank, to_name, to_account, to_bank, datetime, balance }`
- エンジンは**Gemini(画像入力)を第一候補**。理由: 本リポジトリに `GEMINI_API_KEY` と
  `@google/generative-ai` の実装が既にあり、追加契約なしで最速。個人利用の件数なら無料枠で足りる。
  (精度に不満が出たらClaude APIに差し替えられるようプロンプトと出力スキーマは分離しておく)
- 抽出後に**機械検証**を必ず通す: 金額・日付の形式チェック、direction と +/- の整合、
  残高の数値性。検証NGは手動フォームへフォールバック

### 相手口座の自動入力ロジック

1. จากบัญชี/เข้าบัญชี のうち、**設定済みの自分の口座(X-4211)でない側**を相手と判定
2. 相手の 名前・マスク口座番号・銀行名 を `counterparty_*` に自動セット
3. **学習辞書**(`settings.counterparty_rules`): 「この相手はこのカテゴリ」をユーザーが直すたびに記憶
   → 例: "SANGNAPA MANE" → Food を一度直せば、次回から自動でFoodが入る
4. 辞書ヒットしない新規相手はカテゴリ未設定でプレビューに出し、選択させる

## 6. 画面構成(スマホ最優先・3画面)

1. **入力**(ホーム)
   - 上段: 現金クイック入力(金額→カテゴリ大ボタン→登録)
   - 下段: 「スクショ取り込み」ボタン(複数枚可)→ 抽出プレビュー → 一括登録
   - 残高照合の状態表示(「計算残高 = 通知残高 ✓」/ 差額があれば警告+調整提案)
2. **履歴**: 月別一覧(相手・カテゴリ・金額)。タップで編集/削除
3. **集計**: 月次の収入・支出・差引、カテゴリ別内訳、**現行スプレッドシート互換の
   日付×カテゴリ列CSVダウンロード**(移行期はExcel併用できる)

## 7. フェーズ別ロードマップ

| フェーズ | 内容 | 目安 |
|---|---|---|
| **Phase 1 (MVP)** | 雛形コピー→合言葉ログイン+transactions CRUD+現金クイック入力+スクショ取り込み(Gemini解析+学習辞書)+月次集計→ Render+Supabaseで公開 | 実装1〜2日相当。**ここで運用開始** |
| **Phase 2** | LINE転送Bot(スクショをBotに共有→自動記帳+結果返信)。残高照合の自動化 | 実装半日〜1日相当 |
| **Phase 3** | 必要に応じて: スプレッドシート形式CSVの強化、予算アラート、月次レポート、家族・貸し借り管理(シート上部のAine/Pattaya等の個人別残高に相当) | 運用しながら判断 |

## 8. テストと公開

- テスト: devログインで起動→curlでAPI(401/400・重複判定)→実サンプル3枚(入金1・出金2)を
  使った解析の期待値テスト→Playwrightでスマホ画面のUI確認
- 公開: `app-publish` Skillの手順(Render無料プラン+Supabase。**DB必須**=金銭データを消さない)
- 環境変数は `APP_PASSCODE` / `GEMINI_API_KEY` / `DATABASE_URL` / `SESSION_SECRET`。
  追加時は `deploy-check` の4点セット(コード/render.yaml/.env.example/セットアップ手順書)

## 9. 実装開始前の残確認(軽微・実装と並行可)

1. 自分の口座はX-4211の1つだけでよいか(複数口座あれば設定画面で複数登録)
2. QRコード決済(タイのPromptPay等)の通知もSCB Connectに来るはず → 来たらサンプル1枚追加で
   パターン検証する(構造は同じ想定)
3. シート上部の個人別残高(Aine/Pattaya/Eung/Akarasak/Thip)は貸し借り管理か → Phase 3で対応要否
