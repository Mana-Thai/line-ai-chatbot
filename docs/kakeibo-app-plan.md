# 家計簿アプリ(銀行LINE通知連携)制作プラン

グループLINEで使っている注文とりまとめアプリの実証済み構成を雛形に、
**銀行のLINE通知をもとに家計簿を自動更新するWebアプリ**を作るためのプラン。

## 1. 要件の整理

| 要件 | 実現方法 |
|---|---|
| 銀行のLINEアプリの口座情報を元に家計簿を更新 | 銀行がLINEに送る**入出金通知メッセージ**を取り込んで自動記帳(方式は §2) |
| キャッシュ(現金)の買い物は手動入力 | スマホ最適化のクイック入力フォーム(金額+用途で2タップ登録) |
| 立ち上げをできる限り早く・簡単に使える | 注文アプリの雛形(認証・保存層・SSE・デプロイ設定)をコピーして流用。新規開発は「取引」まわりだけ |
| 収支の相手口座内容も自動入力 | 通知文パーサーが振込元/振込先(相手名)を抽出+**学習辞書**でカテゴリまで自動補完(§5) |

## 2. 最重要の設計判断:銀行LINE通知の取り込み方式

銀行のLINE通知(公式アカウントからの入出金通知)には**外部から読み取れる公開APIが無い**。
そのため「通知テキストをアプリに渡す」経路を設計する。段階的に2方式でいく。

### 方式A:コピペ取り込み(Phase 1・MVP)

1. 銀行のLINE通知を長押しコピー
2. 家計簿アプリの「通知貼り付け」欄にペースト
3. パーサーが日付・金額・入出金区分・相手名を自動抽出してプレビュー表示
4. 「登録」を押すだけ(カテゴリは学習辞書が自動提案)

- 実装が最小(テキストパーサー1本+フォーム1画面)で**最速で立ち上がる**
- 複数件まとめてペーストしても1件ずつに分割して取り込む
- Messaging APIの設定・審査が一切不要

### 方式B:LINE転送Bot(Phase 2・自動化)

1. Messaging APIのBotを作り、1対1のトークに追加
2. 銀行の通知メッセージを**Botのトークに転送**するだけ
3. Webhookが通知文をパースして家計簿に自動記帳し、結果を返信
   (例:「✅ 支出 1,200円 / 相手: ○○電力 / カテゴリ: 光熱費 で登録しました」)

- 旧チャットボット(`index.js`)でMessaging APIの実装経験と `@line/bot-sdk` 依存が既にあるため流用できる
- パーサーは方式Aと**完全共通**(`shared/parser.js` に置きサーバー/ブラウザ共用)。
  方式Aで実運用してパーサーの精度を上げてから乗せるので、Bot側の追加実装はWebhook受け口だけ

> **銀行スクレイピングや通知の完全自動読み取りはやらない**(規約・安全性・保守コストの面で不可)。
> 「転送するだけ」が現実的な自動化の上限で、運用負荷はほぼゼロ。

## 3. 全体構成(雛形からの流用)

新しいリポジトリ(例: `kakeibo-app`)を作り、注文アプリからコピーする。

| ファイル | 流用方法 |
|---|---|
| `lib/auth.js` | そのままコピー(LINEログイン+HMACセッション+devログイン) |
| `lib/store.js` | 二重保存層(PostgreSQL/ローカルJSON)+起動時マイグレーションの構造を残し、`orders` を `transactions` に書き換え |
| `server.js` | `requireAuth`・`/api/auth`・`/api/config`・`/healthz`・SSE(`broadcast`+`/api/stream`)を流用。注文APIを取引APIに置き換え |
| `public/` | `api()` fetchラッパ・`escapeHtml`・`openStream`・画面切り替え構造を流用 |
| `shared/constants.js` | カテゴリ一覧・上限値のUMD共用パターン。**`shared/parser.js` を新設**(通知文パーサー) |
| `render.yaml` / `.env.example` | コピーしてサービス名・環境変数を書き換え |

- 認証は**LINEログイン(LIFF)**を推奨。家計簿は個人の金銭データなので合言葉方式より安全で、
  雛形をそのままコピーするだけなので立ち上げ速度も落ちない(`webapp-access-control` Skill参照)
- 開発中は `ALLOW_INSECURE_DEV=1` のdevログインで即動かせる

## 4. データモデル

エンティティは `transactions` 1つから始める(注文アプリの `orders` に相当)。

```
transaction {
  id,
  date,            // 取引日
  type,            // income | expense
  amount,          // 金額(整数)
  source,          // bank_paste | bank_bot | cash(手動)
  counterparty,    // 相手口座/相手名(通知から自動抽出。現金は任意入力)
  category,        // カテゴリ(食費・光熱費・給料 など shared/constants.js で定義)
  memo,            // 任意メモ
  raw_text,        // 取り込み元の通知原文(再パース・重複判定・監査用に保持)
  created_by, created_at, updated_at
}
```

- **重複防止**: `raw_text` の正規化ハッシュ+「同日・同額・同相手」の一致で取り込み時に警告
- **相手→カテゴリ学習辞書**: `settings` テーブル(雛形に既存)に
  `counterparty_rules: { "○○電力": "光熱費", "給与 △△社": "給料", ... }` として保存。
  ユーザーがカテゴリを直すたびに自動で覚え、次回から自動入力される

## 5. 相手口座内容の自動入力(パーサー設計)

`shared/parser.js`(サーバー/ブラウザ共用・UMD)に銀行ごとの通知パターンを定義する。

```
抽出項目: 日付 / 入金・出金 / 金額 / 相手名(振込元・振込先・利用店名) / 残高(取れれば)
```

- パターンは**銀行別の正規表現テーブル**にし、実際の通知サンプルから作る
  (→ Phase 0 でサンプル収集。銀行名・言語:日本語/タイ語も確定する)
- どのパターンにも合わない場合は「金額らしき数字+全文」をプレビューに出し、手動補正して登録
  →補正内容は学習辞書に反映されるので、使うほど自動化率が上がる
- パーサーは純粋関数にして、サンプル通知文に対するテストをcurl/Nodeワンライナーで回す

## 6. 画面構成(スマホ最優先・3画面のみ)

1. **入力**(ホーム)
   - 上段: 現金クイック入力(金額→カテゴリタップ→登録。よく使うカテゴリを大ボタンで)
   - 下段: 通知貼り付け欄(ペースト→自動抽出プレビュー→登録)
2. **履歴**: 月別の取引一覧。タップで編集/削除(SSEで家族の画面にも即反映)
3. **集計**: 今月の収入・支出・差引、カテゴリ別内訳、月次推移。CSVダウンロード

## 7. フェーズ別ロードマップ

| フェーズ | 内容 | 目安 |
|---|---|---|
| **Phase 0** | 銀行のLINE通知サンプル収集(入金・出金・振込の3種以上)、カテゴリ一覧の確定、使う人の確定 | ユーザー作業のみ |
| **Phase 1 (MVP)** | 雛形コピー→ `transactions` CRUD+現金クイック入力+コピペ取り込み+月次集計→ Render+Supabaseで公開 | 実装1〜2日相当。**ここで運用開始** |
| **Phase 2** | 転送Bot(Messaging API Webhook)で通知転送→自動記帳。学習辞書の精度向上 | 実装半日〜1日相当 |
| **Phase 3** | 必要に応じて:予算アラート、タイ語UI(`TH`辞書方式)、複数口座タグ、グラフ強化 | 運用しながら判断 |

早期立ち上げのため **Phase 1 は「手動入力+コピペ取り込み」だけで公開**し、
実際の通知データでパーサーを鍛えてから Phase 2 の自動化に進む。

## 8. テストと公開

- テスト: devログインでサーバー起動→curlでAPI(401/403/400・重複判定・パーサー単体)→
  Playwrightで複数ユーザー同時のUI確認(`order-app-regression` の縮小版)
- 公開: `app-publish` Skillの手順(Render無料プラン+Supabase。**DB必須**=金銭データを消さない)
- 環境変数追加時は `deploy-check` の4点セット(コード/render.yaml/.env.example/セットアップ手順書)

## 9. 着手前にユーザーに確認すること(Phase 0)

1. **どの銀行のLINE通知か**(銀行名と通知の実文サンプル。個人情報はマスクでOK)
2. **使う人は誰か**(夫婦2人だけ? 全員が全取引を見て編集できてよいか)
3. **カテゴリ一覧**(食費・日用品・光熱費・通信費・給料…の初期セット)
4. 通知の言語(日本語/タイ語/英語)— パーサーの正規表現とUI言語に影響
