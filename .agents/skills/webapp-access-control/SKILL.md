# URL共有アプリのアクセス制御

## 大前提: 「URLを秘密にする」は防御にならない

URLはLINEの転送・リンクプレビュー・ブラウザ履歴・スクリーンショットで簡単に漏れる。
**個人情報・金額・名前が載るアプリは、閲覧APIにも必ず認証を付ける。**
「URLを知っている仲間だけ」という運用は、認証の代わりではなく配布方法にすぎない。

## 認証方式の選び方(3択)

| 方式 | 向いているケース | 注意 |
|---|---|---|
| **LINEログイン(LIFF)** | グループLINEで共有し「誰が入力したか」が要るアプリ(注文アプリと同じ)。**迷ったらこれ** | 初期設定30分(`SETUP.md` STEP 2)。LINE外のブラウザでは使えない |
| **合言葉(共有パスコード)** | 個人識別が不要な小さなツール。全員が同じ合言葉を入力→セッション発行 | 「誰が書いたか」は自己申告になる。合言葉変更で全員締め出し可能なのは利点 |
| **閲覧専用のトークン付きURL** | 書き込みが一切ない読み取り専用ページ(結果の公開など)のみ | 書き込みがあるアプリには使わない。トークンは長いランダム値にし、変更できる作りにする |

組み合わせも可: 閲覧は合言葉、管理操作は `ADMIN_PASSCODE` で昇格(注文アプリの `/api/admin` パターン)。

## サーバー側で必ず守ること(注文アプリで実装済みのパターンを流用)

1. **全 `/api/*` に `requireAuth`**。未認証は401。静的ファイル以外に認証なしの口を作らない
2. **権限チェックはサーバーで**。フロントのボタン非表示・disabledは見た目だけの補助。
   書き込み系は「本人 or 管理者」をAPI側で判定して403(`loadEditableOrder` パターン)
3. **セッションはHMAC署名+有効期限**(`lib/auth.js` をそのまま流用)。
   `SESSION_SECRET` は長いランダム値。Renderでは `generateValue: true` が使える
4. **管理者はセッション単位で昇格**: `ADMIN_PASSCODE` 照合→admin付きトークン再発行。
   パスコードの比較・保持はサーバーのみ(フロントに埋め込まない)
5. **入力バリデーション**: 型・範囲・長さ・許可リストをサーバーで検証して400
6. **XSS対策**: ユーザー入力を表示する箇所はすべて `escapeHtml`
7. **秘密はコードに書かない**: パスコード・DB接続文字列・秘密鍵は環境変数のみ。
   `.env` はコミットしない(`.gitignore` 済みか確認)
8. **`ALLOW_INSECURE_DEV` を本番に設定しない**(render.yaml に含めない)

## 公開前チェック(このSkillのレビュー項目)

```bash
# 未認証で全GET/POST/PUT/DELETEが401になるか(200が返る口が1つでもあればNG)
curl -s -o /dev/null -w "%{http_code}\n" https://<アプリURL>/api/<各エンドポイント>
```

- 一般ユーザーのトークンで他人のデータ変更・管理APIが403になるか
- ログアウト状態でSSE(`/api/stream`)に接続できないか(401)
- 画面に `<script>` 等を入力してそのまま実行されないか(エスケープ確認)
- 期限切れトークンが弾かれるか(`exp` チェック)
